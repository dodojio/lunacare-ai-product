01 / BACKGROUND

项目背景

Observation
经期追踪产品已经非常成熟，但 AI 能力增加之后，很多产品仍然把 AI 当成"预测日期"或者"问答助手"。

基于对 Flo Health 的深度竞品分析，一个被行业普遍忽视的问题浮现出来：对于周期不规律的用户（约占女性人群的50%），核心问题从来不是"AI能不能告诉我一个日期"，而是"这个日期到底有多可信？"

Problem
现有产品给出一个确定的预测日期，但不告诉用户这个预测有多准。当预测出错时，用户感受到的不是"AI在学习"，而是"AI在骗我"。
Opportunity
LunaCare 探索：如何让 AI 健康预测更加透明、低焦虑、个性化。不是追求"预测最准"，而是追求"让用户理解不确定性，并知道接下来该做什么"。
02 / PROBLEM DEFINITION

核心问题定义

经过对Flo Health的竞品分析、App Store 2000+条差评的聚类分析、以及学术文献研究，问题收敛为一个 How Might We：

HOW MIGHT WE
help users with irregular periods understand and manage cycle uncertainty without creating unnecessary anxiety?
我们如何帮助周期不规律的用户理解和管理周期的不确定性，同时避免产品制造不必要的健康焦虑？

问题定义的四个维度：

  • 聚焦特定人群：周期不规律的用户，而不是所有女性
  • 聚焦核心矛盾：不确定性的理解与管理，而不是功能堆砌
  • 包含约束条件：不制造焦虑，这是产品设计的红线
  • 开放解决方案：How Might We 不预设答案，允许探索多种可能

04 / PERSONA

核心用户 Persona

LunaCare MVP 阶段聚焦核心用户 Luna。

L
Luna，26岁
互联网公司运营 · 一线城市独居 · 周期不规律

Core Job

"我想提前知道什么时候来，并确认自己的身体变化是不是正常。"

周期状况

25-35天波动，近半年2次推迟超7天，轻度痛经，经前头痛+情绪波动

使用行为

经期前3天每天打开看预测；经期当天记录；推迟时每天多次打开；很少记录症状

核心痛点

预测不准 / 不知道可信度 / 推迟后焦虑 / AI回答太泛 / 记录太麻烦

对AI的期待

"希望AI告诉我这次预测有多准，推迟时帮我分析原因，而不是吓我。"

付费意愿

愿意为"真正准确的预测+个性化建议"付费，但当前AI助手不值这个价

注：Luna 为基于二手研究构建的初始假设 Persona。后续一手研究完成后将根据真实数据修正。

05 / POSITIONING

产品定位

Positioning Statement
LunaCare 是一款以"理解身体的不确定性"为核心的 AI 女性周期健康助手。

重点不是"预测最准"，而是：

// LunaCare 产品理念
Predict with uncertainty — 带着不确定性去预测
Explain why — 解释为什么这么预测
Guide what to do next — 指引接下来该做什么
06 / CORE VALUE

核心价值

LunaCare 的三个核心价值：

🔮
Predict
告诉用户什么时候可能来。基于周期历史+睡眠+压力+运动+症状的多协变量AI预测，输出预测日期+置信区间。
💡
Explain
告诉用户为什么这么预测、这次预测有多可信。置信度透明展示，预测依据可查，数据不足时诚实说明。
🧭
Guide
告诉用户如果情况变化，接下来应该做什么。异常分级预警，明确就医红线，不制造不必要的焦虑。

08 / MVP

MVP 功能规划

LunaCare MVP 包含 4个P0核心功能：

优先级功能说明对应价值
P0 AI周期预测 多协变量预测模型，输出预测日期+置信区间 Predict
P0 Prediction Confidence 置信度透明展示，预测依据可查，数据不足诚实说明 Explain
P0 一键记录 1键记录经期开始/结束，AI自动推荐症状标签 数据基础
P0 异常/不确定性解释 取代"延迟警告"，分级说明+可能原因+行动指引 Guide
P1 AI Companion 对话式健康助手，结合个人数据的个性化回答 Explain + Guide
P1 健康洞察 症状-行为关联分析，周期趋势追踪 Explain
P2 社区/内容 健康知识库，匿名社区讨论 生态
MVP Philosophy
AI Companion 先作为 P1，不是因为不重要，而是因为 Predict→Explain→Guide 的核心闭环必须先跑通。没有准确的预测和透明的解释，AI助手只是一个更会说话的搜索引擎。
09 / USER FLOW

核心用户流程

三个核心用户流程：

Flow A — 首次注册

Onboarding → 周期信息(3步) → Privacy选择 → AI初始预测 → Home
// 设计要点：从Flo的8-10步缩减到3步；隐私选项前置；初始预测诚实标注低置信度

Flow B — 日常记录

Home → Quick Log → 经期/症状确认 → AI Prediction Updated
// 设计要点：核心信息1步完成；AI自动推荐症状标签；记录后即时反馈预测已更新

Flow C — 经期推迟（最关键）

Prediction Date → Delay Detected → Confidence Re-calculated
→ Explain Why (可能原因) → Observe / Consult Doctor
// 设计要点：取代"延迟警告"；分级说明（正常波动/需关注/建议就医）；给行动指引而非制造焦虑

11 / AI PRODUCT LOGIC

AI 产品逻辑

AI 产品逻辑定义输入数据、预测系统、输出结果，以及产品层如何根据不同置信度做差异化处理。

User Data
├─ Cycle History   // 周期历史
├─ Sleep         // 睡眠数据
├─ Symptoms     // 症状记录
├─ Stress        // 压力指数
└─ Activity       // 运动数据
      ↓
Prediction System  // XGBoost + LSTM 混合模型
      ↓
Output
├─ Expected Date    // 预测日期
├─ Prediction Range  // 置信区间（±N天）
├─ Confidence      // 置信度（0-100%）
└─ Explanation     // 预测依据说明
      ↓
Product Layer
├─ High Confidence (≥80%) → normal prediction display
├─ Medium Confidence (50-80%) → show uncertainty explicitly
└─ Low Confidence (<50%) → avoid definitive conclusion, suggest more data
Key Insight
AI 产品不能只考虑 happy path。低置信度时，产品的正确做法不是"给一个看起来确定的答案"，而是"诚实告诉用户我不确定，并建议如何获得更确定的结果"。

14 / VALIDATION

验证方案

🧪 View Validation Plan & Metrics →

通过可用性测试验证设计假设，驱动原型迭代。

可用性测试计划

项目内容
参与者5-8人，优先周期不规律的女性用户
方法远程屏幕共享 + 出声思考（Think Aloud）
任务1查看下一次预测，理解预测可信度
任务2记录今天经期开始，完成一次记录
任务3经期推迟5天，判断是否需要担心，知道接下来该做什么
记录指标任务完成率、完成时间、用户理解度、错误点、用户原话

迭代循环

V1 Prototype → Usability Test → Feedback Synthesis → V2 Prototype
// 通过测试-迭代循环持续优化产品

A/B 测试计划（上线后）

  • 置信度展示方式：进度条 vs 百分比 vs 文字描述，对用户理解度和焦虑感的影响
  • 推迟场景文案：分级说明 vs 传统警告，对用户焦虑感和行动率的影响
  • AI推荐症状：AI推荐 vs 手动选择，对记录完成率和记录丰富度的影响
